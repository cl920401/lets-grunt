# Spec (documentation only)

Follow **Step gate chosen in Plan**, **Self-review before asking for the next step**, **Authority and audit trail**, **Independent review before asking a human**, and the single **Numbered milestones** list in the shared workflow. Authorization mode is the default; Trust mode can request the next in-scope confirmation without an owner ping or re-entry, but still waits for fresh exact-step confirmation and quorum. The invocation itself never grants authority.

Run this mode only under explicit user direction. Read **Project filesystem boundary**, Specification and Handoff in `references/WORKFLOW.md` through authorized skill access. If it is missing, stop without changing files. Bind reads, searches and authorized document writes to the verified project root. Apply the same limits to independent reviewers and wait for the project initiator's explicit approval before any outside access.

On entry or resume, follow the shared **Plan, Spec and Build transitions**. Reuse the supplied project root and recorded mode once independently verified. Mode 2 means Trust with confirmation from any one verified eligible project participant, subject to any stricter recorded policy. A known root or mode does not authorize a numbered step or outside access. Recover the existing discussion and step state. Check source evidence for facts and clarify only material Plan decisions that remain open before dependent work. Keep valid decisions and prior reviews. State reversible assumptions and continue the current authorized step. Apply the same diagnosis when preparing the Build handoff. Ordinary step review checks the current deliverable, phase constraints, evidence and risk.

Use steps **4–9** separately: product specification → architecture → API/UI → data/DDL → test methods → cross-check and freeze. Align security, privacy, performance and reliability criteria or record why each is N/A. Capture decisions and reviewer expectations before handing off the pinned design. Scale the detail to risk and explain any N/A item. For existing systems, follow **Scope the change, not the whole system**: verify the changed behavior plus relevant invariants, and design deeper recovery checks only where the risk calls for them. Write only the documentation paths the user authorizes; otherwise return a draft. DDL belongs in a Markdown review draft, not a migration file. Skeleton design belongs to Build. Do not create source stubs, run tests or SQL, write source/tests/configuration, change the environment or start execution. Report the exact version and readiness; do not advance to Build.

Follow **Plan and Spec reply order**. Show the in-scope design and confirmed decisions first, with reversible assumptions inline. Put material questions, viable options, main impact and any recommendation under **Needs your decision** in the user's language at the end. Prefer a native question card when supported. Use text instead when the card is unavailable or confirmed unsent. Each question should be answerable where it appears. Keep step authorization, initiator confirmation and missing evidence separate. Keep the handoff open while a required reply is pending.

At #9, follow the shared **Spec #9 outcome walkthrough and confirmation**. Obtain or verify an independent read-only assessment of the actual pinned SPEC and its value, direction and tradeoffs. After it passes, walk through a typical path and a critical failure or recovery path on paper. Give the initiator a short result card in their language: what they get, what happens on failure, and what remains unverified or out of scope. Ask whether that outcome meets their needs. Reuse complete same-version evidence. Freeze only after the verified initiator explicitly confirms the outcome of that exact version. Keep confirmation outside the pinned SPEC. Once #9 is complete, give a single manual Build hint on the last line using **Manual next step by host**. Keep the next phase's milestones and approval mechanics in the working record. Build still requires its own authorization.
